__Самая главная проблема иключений &mdash; невозможность для 
вызываемого кода (`callee`) определить &laquo;исключительность&raquo; ситуации 
для вызывающего кода (`caller`). В итоге устойчивые к ошибкам программы 
используют исключения как новый механизм управления потоком исполнения.__

### Хрупкость (Fail-fast) и устойчивость (Fault-tolerate)
Разделим программы на две категории по отношению к тому, как они поступают
с ошибками при работе:
  - __хрупкие__ или __fail-fast__ программы завершают своё исполнение при 
первой же неясной ситуации, если есть хоть какое-то подозрение, что продолжить 
работу нельзя &mdash; программа должна завершиться;
 - __устойчивые__ или __fault-tolerate__ программы стремятся как можно дольше 
сохранять работоспособность, если есть хоть какая-то возможность продолжить 
работу &mdash; программа должна работать.

Разумеется некоторая произвольная программа в различных местах может 
принадлежать различным классам, программы не бывают полностью хрукими или 
абсолютно устойчивыми, но для дальнейших рассуждений нам будет удобно 
обращаться именно к таким классам.

### Хрупкие программы и исключения
Хрупкие программы имеют интересную особенность: у них всегда есть один __happy
path__ или путь с небольшой разветвлённостью, отклонения от этого пути 
невозможны. Такая программа или каждый шаг завершает успешно и достигает 
конца или не имеет результата. Например рассмотрим простую последовательность
действий:
  1. прочитать данные из файла;
  2. обработать данные;
  3. записать данные в файл.

Пренебрегая обработкой ошибок наш __happy path__ выглядел бы так:
```java
BufferedReader br = new BufferedReader(new FileReader("in.txt"));
String inputLine = br.readLine();
br.close();

String resultLine =
    processLine(inputLine);

BufferedWriter bw = new BufferedWriter(new FileWriter("out.txt"));
bw.write(resultLine);
bw.close();
```

Хрупкую программу не интересует, что на некотором шаге может произойти ошибка.
Если файл не удастся открыть для чтения, то просто завершись. Если `inputLine` 
оказалась `null` или `empty` &mdash; завершись! Не удалось открыть файл для 
запись &mdash; просто завершись! У *абсолютно хрупкой* программы нет *логики* 
обработки ошибок, программа должна разрущиться. Если бы мы использовали для 
такой программы проверки возвращаемого изначения, то наш код просто &laquo;
загрезнился&raquo; бы синтаксическим шумом `if () { } else { }`.

Для таких программ исключения (exceptions) &mdash; это великолепный выход! 
Пусть каждая функция переводит программу в аварийный контекст. 
В примере выше нам вообще ничего не нужно делать: достаточно добавить в 
`main` `throws IOExcption` для `checked exception` и программу можно 
использовать. Программа либо успешно выполнится, либо остановится и мы увидим 
трейс возникшей ошибки.

__Хрупкие программы и функции выигрывают с механизмом исключений.__

### Устойчивые программы и исключения
С учтойчивыми программами всё не так просто. Устойчивые программы стремятся 
сделать любой путь выполнения программы &laquo;счастливым&raquo;. Теперь мы 
не просто читаем данные из файла: мы пытаемся прочитаь, *но* если не смогли, то
читаем из другого, *но* если не смогли, используем строку по умолчанию. 
Таких __backup path__ может быть очень много на каждую ошибочную ситуацию.
Наша новая, устойчивая программа пытается получить и обработать строку из 
разных файлов. Нам приходится обернуть вызов в блок `try`, чтобы просто 
отбросить исключение и перейти к следующему файлу. Если чтение успешно, то нам 
следуем освободить ресурс файла и перейти к работе с данными, где так же может
возникнуть ошибка, которую мы вновь &laquo;спрячем под ковёр&raquo; и 
перейдём к следующему файлу.
Пример:
```java
String resultLine = null;
final List<String> backupFiles = List.of("in-1.txt", "in-2.txt", "in-3.txt");
final String defaultLine = "Hello World!";

for (String fileName : backupFiles) {
    String inputLine = null;
    try (BufferedReader br = new BufferedReader(new FileReader(fileName))) {
        inputLine = br.readLine();
    } catch (Exception e) {
        System.out.println(e.getMessage());
        continue;
    }
    
    try {
      resultLine =
        processLine(inputLine);
    } catch (Exception e) {
      System.out.println(e.getMessage());
      continue;
    }

    break;
}

if (null == resultLine) {
    try {
      resultLine = 
        processLine(defaultLine);
    } catch (Exception e) {
      System.out.println(e.getMessage());
      resultLine = defaultResult;
    }
}
// ... code continues ...
```

В коде выше `try () { } catch { }` блоки используются как управляющие 
конструкции `if () { } else { }`, что полностью нивелирует их ценность. 
В `C++` это также привело бы к неоправданной трате ресурсов. 

Возникшая проблема связана с тем, что для программ, у которых  __happy path__ 
сильно разветвлён и содержит сложную логику *обхода* ошибочных ситуаций, 
исключения не уменьшают даже видимую сложность логики кода, а наоборот &mdash;
увиличивают.

Для устойчивых программ выгоднее была бы логика с возвращаемыми значениями или
`Optional`/`Result` механизмом. Если вообразить, что наши Java функции НЕ
выбрасывали бы исключения, а возвращали опциональные значения, то код выглядел 
бы так:
```java
Optional<String> resultLine = Optional.empty();
final List<String> backupFiles = List.of("in-1.txt", "in-2.txt", "in-3.txt");
final String defaultLine = "Hello World!";

for (String fileName : backupFiles) {
    Optional<BufferedReader> br = BufferedReaderFactory.fromFilename(fileName);
    if (!br.isPresent()) continue;

    Optional<String> inpuLine = br.get().readLine();
    br.get().close();
    
    if (!inpuLine.isPresent()) continue;

    resultLine = 
      process(inputLine);
    if (resultLine.isPresent()) break;
}

if (!resultLine.isPresent())
  resultLine =
    process(defaultLine);
// ... code continues ...
```
Даже в таком императивном виде, по моему мнению, код стал короче и более 
понятным, а его логика стала прозрачной.

__Устойчивые программы не получают ни в визуального, ни когнитивного снижения
сложности кода при использовании исключений, но могут существенно потерять 
в читаемости и производительности.__

> Интересно, что с точки зрения хрупкой программы код с использованием
>`Optional` в Java будет таким же простым, как с исключениями, благодаря тому,
>что вызовы `.get()` на `Optional` генерируют исключения.

### Основная проблема исключений
Здорово, если в хрупкой программе используются исключения. Плохо, если 
исключения используются в устойчивой программе. Но основная проблема 
заключается в том, что разработчик библиотечной системы классов для работы с 
файлами не знает какой код будет работать с его библиотекой. Может быть это 
будет хрупкая программа и нужно выбрасывать исключения. Может быть это будет 
устойчивая программа и нужно без выхода в аварийный контекст сообщать об ошибке
через возвращаемое значение. __`Callee` не обладает информацией и компетенцией,
чтобы диктовать способ обработки собственных ошибок `caller`.__ Это и есть 
самая губительная для исключений проблема. В &laquo;продуктовом&raquo; коде 
больше мест устойчивых, чем хрупких. Потому некая библиотечная функция, 
выкидывающая исключение по собственному усмотрению, становится скорее неудобной,
чем полезной. Для функции, которая интенсивно испльзуется в различных вызовах, 
для библиотечной функции, следовало бы всегда генерировать значение в качестве
ошибки, а не исключение.
