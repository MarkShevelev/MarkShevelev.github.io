### Тезис
Имена идентификаторов должны быть максимально короткими при сохранении 
однозначности смысла для связанного объекта в рамках ограниченного контекста.

#### Длинные имена повышают сложность
Мы все понимаем, что *читать* код приходится гораздо больше, чем *писать* код.
Мы очень много говорим о том, что имена переменных и функций должны быть 
*информативными* и рассуждаем в ключе: короткие имена &mdash; плохо; длинные 
имена &mdash; хорошо. Однако длинные имена сложнее воспринимать просто потому,
что они длиннее! Короткие же имена воспринимаются проще и удерживать в голове 
идентификатор из одной-трёх букв проще, чем из 10. Имена `src`, `dst`, `idx`, 
`it`, `buf` гораздо удобнее, чем `source_memory_first_byte_address`, 
`user_information_array_index` и т.п. Информативны ли эти длинные имена? Да!
Но&hellip; Но мы не будем держать их полностью в памяти, когда читаем код. 
Посмотрите на следующий фрагмент кода:
```cpp
size_t user_information_array_index = 0;
for (; 
  user_information_array_index != const_user_information_array_size;
  ++user_information_array_index)
{
  if (
    const_user_age_maximal_age_including >=
      user_information_array[user_information_array_index].age
    &&
    const_user_age_minimal_age_including <=
      user_information_array[user_information_array_index].age
  )
    break;
}
```
Нам ясно, что здесь происходит, но *информативные названия* создают много 
&laquo;синтаксического шума&raquo;. Нам постоянно повторяют:
индекс отностится к массиву `user_information_array`, границы поиска являются 
неизменяемыми значениями, границы поиска включены в промежуток поиска, мы 
делаем фильтрацию именно по возрасту и т.п. Давайте посмотрим на 
этот же фрагмент, но чуть-чуть иначе.

#### Контекст
```cpp
uint32_t index = 0;
for(; index != size; ++index)
  if (maximal >= users[index].age && minimal <= users[index].age)
    break;
```
Читать сам код цикла стало гораздо проще: названия короче, они отражают суть 
происходящего. Какую информацию мы потеряли? Мы не знаем являются ли значения 
имзменяемыми, мы не знаем, что это именно `user_information`, а не 
`user_statistics` или что-то иное, мы не знаем должны ли быть включены границы 
поиска в фильтрацию.
Если же мы посмотрим чуть-чуть шире, то найдём ответы на свои вопросы:
```cpp
uint32_t
user_information_array_age_boundary_included_first_index_get
(
  uint32_t const minimal, 
  uint32_t const maximal,
  user_information_t const *users,
  size_t const size
)
{
  uint32_t index = 0;
  for(; index != size; ++index)
    if (maximal >= users[index].age && minimal <= users[index].age)
      break;

  return index;
}
```
Функция своим названием, типами входящих данных и исходящим типом даёт нам 
необходимую дополнительную информацию. Таким образом, чем больше у нас 
окружающего контекста, тем меньше нам нужно вкладывать информации в сам 
идентификатор. Например ниже представлен код, где переменные именуются 
однобуквенно, но все действия предельно понятны:
```cpp
void
ip4_addresses_swap(ip4_address_t *s, ip4_address_t *d)
{
  ip4_address_t _t, *t = &_t;
  memcopy(t, s, sizeof(_t));
  memcopy(s, d, sizeof(_t));
  memcopy(d, t, sizeof(_t));
}
```
Контекстом для наших идентификаторов можеть быть:
  - окружающий блок кода;
  - функция или метод;
  - класс или файл;
  - `namespace` или `package`;
  - модуль или доменный контекст.

#### Имя и область видимости
Важно понимать, что хорошее название идентификатора для одной области 
видимости, может оказаться неудачным для для другой. Например, если у нас 
есть однобуквенный счётчик `i`, то он вполне приемлем для переменной, 
отсчитывающей итерации в цикле, но идентификатор `i`, живущий 
в рамках функции на сотни строк, может оказаться недостаточно информативным. 
Если мы имеем дело с глобальным идентификатором, живущим на самом верхнем 
уровне доменной модели, то ему просто неоткуда взять контекст, кроме общей 
документации вашего приложения, он *обязан* быть максимально информативным. 
Но и спользоваться этот идентификатор не будет очень часто. На верхнем уровне 
у нас может жить идентификатор `PaymentProcessingUser`, связанный с классом 
в рамках контекста платежей. Когда же мы получаем экземпляр этого класса в 
методе, название для идентификатор объекта может быть коротким, 
так как время его жизни мало:
```java
public PaymentProcessingTransaction
prepare(PaymentProcessingUser u) {
  u.invokeMethod();
  //...
}
```
Если метод достаточно длинный и у нас могут возникать неоднозначности, имя 
можно расширить:
```java
public PaymentProcessingTransaction
prepare(PaymentProcessingUser usr) {
  // a log of code ...
  usr.invokeMethod();
  // a log of code ...
  usr.invokeMethod();
  // a log of code ...
}
```

#### Принятые сокращения
Очень хорошей практикой, по моему мнению, является некоторая таблица 
__принятых в проекте сокращений__. Очень часто мы сталкиваемся с похожими 
сущностями в разных частях кода: пользователь, пакет, источник, отправитель,
заголовок, товар и т.д. Разумно создать для них таблицу удобных 
трёх-четырёхбуквенных сокращений и занести в документатицию.
|сокращение|описание|
|----------|--------|
| `u`, `usr` | для пользователей |
| `pk`, `pkt` | сетевой пакет |
| `s`, `src` | источник данных |
| `s`, `sndr` | отправитель сообщения |
| `h`, `hdr` | заголовок |
| `p`, `prd` | товар |
| `r`, `rsv` | получатесь сообщения |
| `rv`, `ret` | возвращаемое значение |

Команда сможет придерживаться этих сокращений во всех частях проекта. 

#### Владение кодом и погружение в контекст
Самая напряжённая борьба в именованиях идентификаторов идёт между теми, кто 
*владеет кодом*, и теми, кто часто *погружается в контекст*.
Человк, владеющий кодом, скорее всего, желает работать с именами покороче. 
Длинные имена создают &laquo;шум&raquo; из символов, за которыми не видно 
алгоритмов. Владеющий кодом человек всегда в контексте.
```java
t.commit(u, rlMsg, pd);
```
Человек же, увидивший код впервые, несомненно, теряется. У ного в голове нет 
контекста. Если такой прогрммист словил `NullPointerException` в строке кода,
он хочет сразу видеть много контекста:
```java
preparedPaymentTransaction.commit(
  paymentContextUser, rollbackMessage, paymentDetails);
```

Недавно мне случайно попалось видео, в котором автор предлагала по коду 
угадать, предположить, из какой игры был вырван цикл, точнее метод. Выглядел 
метод примерно так:
```java
List<int[]> getThem() {
  List<int[]> list1 = new ArrayList<int[]>();
  for (int[] x : theList)
    if (x[0] == 4)
      list1.add(x);
  return list1;
}
```

Затем автор предложила рефакторинг названий, который должен был помочь. 
Результат получился примерно такой:
```java
List<int[]> getFlaggedCells() {
  List<int[]> flaggedCells = new ArrayList<int[]>();
  for (int[] cell : gameBoard)
    if (cell[STATUS_VALUE] == FLAGGED)
      flaggedCells.add(cell);
  return flaggedCells;
}
```

Как я не смотрю на этот код, не вижу, чтобы нам стало особенно понятнее 
&laquo;угадать&raquo; игру. Однако сама постановка вопроса и то, как 
выполнено переименование, хорошо показывает, что думают программисты, которых 
волной `NullPointerException` занесло в кусочек кода, которым они в моменте не 
владеют: им хочется мгновенно получить как можно больше контекста. Хотя этот 
контекст уже есть, нам просто нужно взглянуть шире: на класс, пакет или 
открыть документацию.

Зачем нам называть набор элементов `flaggedCells`, если это уже говорит метод?
Гораздо разумнее назвать список `res` или `ret`, так как в контексте метода 
&mdash; это результат вычислений, название же метода подскажет, что именно за 
результат мы ожидаем. Мы могли бы оставить название переменной перебора `x` и 
никак не потеряли бы смысл. __Именование &laquo;магических констант&raquo; 
&mdash; это несколько другой вопрос и здесь он очень уместен.__ 
Равно как и выделение типа для `int[]`, например в `Cell`, которое автором не 
было предложено, вероятно, из педагогических соображений.
Давайте сделаем это!
```java
List<Cell> getFlagged() {
  List<Cell> ret = new ArrayList<Cell>();
  for (Cell c : board)
    if (c.staus() == FLAGGED)
      ret.add(c);
  return ret;
}
```
На мой взгляд метод стало проще читать и понимать. Алгоритм слишком прост, 
чтобы засорять его длинными названиями.
